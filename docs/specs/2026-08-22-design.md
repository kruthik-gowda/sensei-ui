# Sensei Review UI — Design

**Date:** 2026-08-22
**Status:** Approved, pending implementation plan

## Problem

Sensei generates good review findings but offers no way to inspect or shape them
before they reach a colleague's merge request. Its CLI prints a wall of text and
a three-way `approve / edit / discard` prompt covering the whole review at once.
A reviewer who agrees with nine findings and disagrees with the tenth must
accept all ten or discard all ten.

A scheduled variant that posts autonomously on a daily timer removes the
reviewer from the loop entirely, which makes two failure modes expensive:

1. **False positives reach colleagues unreviewed.** A run on 2026-08-21 produced
   findings that were demonstrably wrong when checked against the diff.
2. **Stale findings are argued against fixed code.** In the same session, ten
   review threads were posted, then the author pushed a commit addressing them;
   the findings were only recognised as obsolete by manual re-checking.

This project replaces the scheduler with an on-demand web UI where findings are
triaged, edited, and posted deliberately.

## Goals

- Inspect every generated finding before anything is posted
- Edit comment text in place, against the diff it refers to
- Show exactly what will be posted and to which destination
- Make staleness impossible to miss
- Install and run with one command, on any teammate's machine
- Post under each reviewer's own GitLab identity

## Non-goals

- **Hosted multi-user service.** Would require per-user GitLab OAuth, an
  org-billed Claude key, sessions, and secret storage. Local-first avoids all of
  it: each reviewer runs their own copy with their own credentials.
- **Real-time collaboration.** Two reviewers on one MR is rare; merge semantics
  would cost more than the triage loop itself.
- **Replacing sensei's CLI.** `sensei review` remains fully supported. This is an
  additional entry point over the same engine.
- **Background scheduling.** Dropped deliberately; the UI is on-demand.
- **Reimplementing review generation.** Duplicate-suppression, inline placement,
  and the style profile already work in sensei. Depending on them is the point.

## Approach

`sensei-ui` is a **standalone application that depends on sensei as a library**,
in its own repository with its own release cycle.

The alternative considered was building the UI inside the sensei repository as a
`sensei serve` command. That would have given a single install and legitimate
access to sensei's internals. It was not chosen: sensei is a fork of an upstream
project, and coupling the UI's release cycle to it means every UI change carries
a merge burden against upstream, or waits on upstream review.

The cost of standing alone is real and is addressed explicitly below under
**Engine boundary**: sensei's posting path is currently private API, so this
project must either isolate that coupling or upstream a public interface.

## Architecture

```
src/sensei_ui/
  __main__.py     CLI entry point: `sensei-ui` starts the server
  app.py          FastAPI application: REST endpoints + SSE progress
  engine.py       THE ONLY module that imports sensei internals
  store.py        SQLite persistence (~/.sensei-ui/ui.db)
  diff.py         Unified-diff parsing into side-by-side rows
  verify.py       Claude adjudication pass (annotates findings)
  setup.py        First-run health checks and guided configuration
  static/         Prebuilt React bundle (committed to the repo)
ui/               React source; only touched when developing the UI
tests/            pytest
```

`sensei-ui` starts uvicorn bound to `127.0.0.1` and opens a browser.

Python >= 3.9, matching sensei, so the two can share an environment.

### Engine boundary

Every call into sensei is confined to `engine.py`. Nothing else in the codebase
imports from `sensei.*`.

This matters because the function this project most needs —
`sensei.cli._post_review_results` — is private, underscore-prefixed, with no
stability guarantee. Scattering that dependency across modules would mean a
sensei upgrade breaks the app in several places at once, at posting time, on a
colleague's merge request.

Two mitigations, in order of preference:

1. **Upstream a public interface.** Open a PR against sensei adding
   `sensei.posting.post_review(...)` as a public function, with the existing
   private helper delegating to it. Then depend on `sensei-review>=<version>`
   and drop the private import entirely. This is the durable fix and should be
   attempted first.
2. **Contract tests until that lands.** `tests/test_engine_contract.py` asserts
   that each sensei symbol `engine.py` relies on still exists and still accepts
   the arguments passed. A sensei upgrade then fails loudly in CI rather than
   silently at post time.

The engine boundary is also what keeps a hosted mode possible later without a
rewrite, though that is explicitly out of scope.

## Data model

Two sources of truth, deliberately separated:

- **Sensei's snapshots** (`~/.sensei/reviews/*.json`) remain the record of what
  the engine *generated*. This project reads them and never writes them.
- **SQLite** (`~/.sensei-ui/ui.db`) is the record of what the reviewer *decided*.

The separation is required, not stylistic: `sensei review` always regenerates
findings and merges its cached snapshot back in, so a snapshot cannot hold a
decision — a re-run would overwrite it.

Storing under `~/.sensei-ui/` rather than `~/.sensei/` keeps this project's
state out of a directory another tool owns.

```sql
CREATE TABLE run (
    id            INTEGER PRIMARY KEY,
    project_path  TEXT NOT NULL,
    mr_iid        INTEGER NOT NULL,
    mr_url        TEXT NOT NULL,
    head_sha      TEXT NOT NULL,
    created_at    TEXT NOT NULL,
    status        TEXT NOT NULL,  -- running | complete | failed
    verify_status TEXT NOT NULL,  -- ok | skipped | failed
    test_summary  TEXT            -- JSON; the consolidated coverage table
);

One run row per merge request. Re-reviewing repoints that row at the new head
SHA rather than minting a new one, which is what keeps the finding merge below
— and therefore every reviewer decision — alive across regeneration.

CREATE TABLE finding (
    id             INTEGER PRIMARY KEY,
    run_id         INTEGER NOT NULL REFERENCES run(id),
    signature      TEXT NOT NULL,
    file           TEXT NOT NULL,
    line           INTEGER,
    kind           TEXT NOT NULL,  -- must | nit | test
    confidence     INTEGER,
    original_body  TEXT NOT NULL,
    edited_body    TEXT,
    state          TEXT NOT NULL,  -- pending | kept | discarded | posted
    verdict        TEXT,           -- confirm | reject | NULL
    verdict_reason TEXT,
    discussion_id  TEXT,
    posted_at      TEXT
);

CREATE UNIQUE INDEX finding_run_signature ON finding (run_id, signature);
```

### Signatures

Two identities are involved and they are deliberately not the same value.

**Remote identity** is sensei's `build_body_signature` /
`build_inline_signature` from `gitlab_client.py` — exactly what
`get_existing_comments` returns, so this project's idea of "already handled"
can never disagree with GitLab's. It is derived from a finding's own `file` /
`line` fields at posting time, never parsed back out of stored text.

**Storage identity** is that value plus a short hash of the *normalised* body.
The hash is required because an inline remote identity is only `(file, line)`:
two `must` findings on one line share it, and a store keyed on it alone would
UPSERT one over the other and lose a finding between generation and the
reviewer. Normalising before hashing means whitespace churn in regenerated text
does not mint a new row, so **edits and discards survive regeneration** rather
than resetting.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/health` | Credential and dependency status |
| `POST` | `/api/setup` | Persist configuration from the wizard |
| `GET` | `/api/mrs` | Open MRs where the user is reviewer or assignee |
| `POST` | `/api/runs` | Start a review; returns `run_id` immediately |
| `GET` | `/api/runs/{id}/events` | SSE progress stream |
| `GET` | `/api/runs/{id}` | Run, findings, and parsed diff |
| `PATCH` | `/api/findings/{id}` | Update `edited_body` or `state` |
| `POST` | `/api/runs/{id}/post` | Post kept findings |
| `POST` | `/api/runs/{id}/unpost` | Delete threads created by this run |

Candidate MRs are the union of `reviewer_username` and `assignee_username`
queries against the configured group, deduplicated by MR id.

## Diff handling

GitLab returns unified diffs. Side-by-side rendering requires pairing them into
left/right rows, and that pairing determines which line a comment anchors to.

**Parsing happens in Python, not React.** Line mapping is the one piece of this
system that can put a comment on the wrong line of someone else's MR, so it
belongs where it can be unit-tested against real diffs. `diff.py` parses with
`unidiff` into an explicit row structure:

```python
{"kind": "context" | "add" | "del" | "meta",
 "old_line": Optional[int], "new_line": Optional[int], "text": str}
```

React renders that structure without interpreting it. The same parsed output
feeds both rendering and anchor validation, so what the reviewer sees and what
gets posted derive from one computation.

Findings whose line is absent from the diff cannot anchor an inline thread.
These are detected with sensei's `extract_diff_lines` and shown as demoted to
the summary comment before posting, never silently relocated.

## User flows

### First run

`sensei-ui` on an unconfigured machine opens a setup wizard rather than failing.
Each prerequisite is checked and fixed in-page:

1. **GitLab PAT** — pasted, then verified with a live API call that displays the
   authenticated username, so a wrong-account token is caught immediately.
2. **Claude CLI** — probed with a single-token prompt. On failure the wizard
   shows the exact `claude /login` remediation rather than a raw error.
3. **Style profile** — offers to run `sensei learn` if none exists.
4. **Sensei itself** — verifies an importable, compatible version is installed,
   since this project cannot function without it.

The same checks back a persistent health indicator. A revoked token surfaces as
one banner instead of an unexplained per-file error on every file in a review.

### Triage

The reviewer's loop is: read finding, judge it, adjust wording, move on. The UI
is built around that loop and is keyboard-first — `j`/`k` move between findings
with the diff scrolling to each anchor, `a` accepts, `d` discards, `e` edits,
`?` shows the key map. Progress reads "7 of 23 triaged."

The Claude verification pass **annotates rather than decides**. Confirmed
findings arrive pre-accepted; rejected ones arrive pre-discarded but visible,
each showing its reasoning, one keystroke from rescue. On a clean review the
reviewer accepts a few and posts. Nothing is hidden and no finding is dropped
without being seen.

### Posting

A mandatory preview renders each comment as it will appear, grouped by
destination: must-fix as inline threads, nits as one summary comment,
test-coverage as a single table, plus any off-diff findings demoted to the
summary.

**Staleness blocks posting.** Every run records the head SHA it reviewed. If the
MR has moved, posting is disabled behind a "re-review at `<sha>`" action. This
is a hard block rather than a warning because posting against superseded code is
the most expensive failure this tooling has actually produced.

## Error handling

- **Partial posting.** Each finding's state and discussion id are written as it
  posts, so an interruption leaves the remainder retryable. Retry keys off the
  same signatures used for GitLab dedup, so a re-run cannot double-post.
- **Undo.** `unpost` deletes the discussions a run created, using stored ids.
  Reversibility is what lets a reviewer move quickly.
- **Verification failure.** If the Claude pass times out or returns unparseable
  output, the run records `verify_status = failed`, findings arrive unannotated,
  and the UI says so. It never silently posts or drops.
- **Engine failure.** A failed run is recorded with `status = failed` and its
  stderr tail, visible in the inbox rather than lost to a log file.
- **Sensei incompatibility.** If the installed sensei is missing a symbol
  `engine.py` needs, the app reports it at startup with the version it found and
  the version it expects, rather than failing mid-review.

## Testing

Effort concentrates on the logic that can affect someone else's MR:

- **Diff parsing** — golden-file tests over real MR diffs, covering renames,
  new files, deletions, and multi-hunk files. Asserts every row's `old_line` /
  `new_line` mapping.
- **Anchor validation** — a finding off the diff is demoted, never relocated.
- **Store merge** — an edited body and a discarded state both survive a
  regenerating re-run.
- **Idempotency** — posting the same run twice creates threads once.
- **Engine contract** — every sensei symbol relied on exists and accepts the
  arguments passed. This is what makes the private-API dependency survivable.
- **Setup checks** — each health probe reports correctly for pass and fail.

The React layer stays deliberately thin so it needs little testing; the risky
logic lives in Python where tests are cheap.

## Distribution

```bash
pip install sensei-review sensei-ui
sensei-ui
```

Two packages, because this project depends on sensei rather than living inside
it. `pipx install sensei-ui` also works if sensei is already on the path.

The React bundle is committed, so running the UI requires no Node toolchain.
Only `ui/` development needs npm. Each teammate supplies their own GitLab PAT
and Claude auth, so comments post under their own identity and no credential is
ever shared.

## Migration

The launchd job (`com.kruthikgowda.sensei-review`) and its scripts
(`~/.sensei/scheduled_review.py`, `verified_review.py`, `scheduled_review.sh`)
are superseded. Their verification logic moves into this project's run pipeline;
the scheduling and auto-posting are dropped by design. Unloading the job is part
of implementation:

```bash
launchctl unload ~/Library/LaunchAgents/com.kruthikgowda.sensei-review.plist
```

Existing snapshots in `~/.sensei/reviews/` remain readable; the UI ingests them
on first launch so past reviews appear in the inbox without a re-run.

## Risks

- **Private-API drift.** The live risk of standing outside sensei. Mitigated by
  the single-module engine boundary and contract tests, and resolved properly by
  upstreaming a public `post_review` interface.
- **Two-install friction.** Teammates must install two packages instead of one.
  Mitigated by a single documented command and a startup check that names the
  missing piece.
- **Committed build artifacts.** The `static/` bundle must be rebuilt on UI
  changes; a stale bundle ships silently. A CI build check is the answer if this
  proves annoying in practice.
